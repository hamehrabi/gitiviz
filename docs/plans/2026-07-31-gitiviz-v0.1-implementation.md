# Gitiviz v0.1 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** A Claude Code plugin that turns any Git branch/commit range into a plain-language, evidence-backed, self-contained HTML change book.

**Architecture:** TypeScript pnpm workspace that is simultaneously a Claude Code plugin and its own marketplace. Deterministic analysis (git layer + TS/JS analyzers + evidence graph) runs in bundled dependency-free `.mjs` scripts; Claude narrates facts through a validated request/response loop; a renderer emits one offline HTML file. All dev tooling runs inside Docker (`node:22-bookworm`) — the host has no Node/npm and must never need it.

**Tech Stack:** TypeScript, pnpm (via corepack in Docker), vitest, esbuild (bundling to single-file `.mjs`), Ajv (bundled into validate script only), plain `git` CLI via `execFile` (no shell interpolation), zero-dependency runtime scripts.

**Design doc:** `docs/plans/2026-07-31-gitiviz-design.md` (approved). Read it before starting.

**Non-negotiable constraints (from design):**
- Never run `npm`/`node` on the host — every toolchain command goes through `./dev.sh` (Docker).
- Runtime scripts committed under `plugins/claude-code/scripts/*.mjs` must be dependency-free single files.
- Repo strings (paths, labels, snippets) are hostile: never pass through a shell, always escape before HTML.
- Every claim in a manifest carries provenance: `declared | derived | inferred | unknown`. AI output can never be `derived`.
- Output goes to the analyzed project's `.gitiviz/`, never into the plugin directory.

## Phase 4 — Analyzers (`@gitiviz/analyzers`)

### Task 8: Analyzer interface + package analyzer

**Files:**
- Create: `packages/analyzers/src/types.ts`, `packages/analyzers/src/packageAnalyzer.ts`
- Test: `packages/analyzers/src/packageAnalyzer.test.ts`

Interface (language-neutral, evidence-first):

```ts
export interface Analyzer {
  id: string;               // e.g. "js-package@1"  — id includes version for cache keys
  appliesTo(path: string): boolean;
  analyze(input: { path: string; content: string }): AnalyzerFact[];
}
export interface AnalyzerFact {
  kind: "package" | "import" | "export" | "route" | "sql-table";
  value: Record<string, string>;
  anchor: { path: string; startLine: number; endLine: number };
}
```

Package analyzer: parses `package.json` (JSON.parse in try/catch — malformed files produce an `analysisLimitations` entry, never a crash), emits package name/deps facts. TDD with fixture content.

Commit: `feat(analyzers): analyzer interface + package analyzer`.

### Task 9: Import/export analyzer (regex-based, honest about limits)

Line-based extraction of `import ... from "x"` / `export function|const|class NAME`. Explicitly documented limitation (recorded in `analysisLimitations`): no full AST parse in v0.1; dynamic imports and re-exports are best-effort. Tests: standard imports, multi-line import, hostile symbol names survive as data (no eval, no regex catastrophic backtracking — cap line length at 2000 chars).

Commit: `feat(analyzers): import/export analyzer`.

### Task 10: HTTP route analyzer

## Phase 5 — Core (`@gitiviz/core`)

### Task 11: Evidence graph builder

**Files:**
- Create: `packages/core/src/graph.ts`
- Test: `packages/core/src/graph.test.ts`

Input: `FileChange[]` + `AnalyzerFact[]` for base and head sides. Output: `Entity[]` + `Relationship[]` with stable IDs (`sha1(kind + technicalLabel)` truncated), base/head states computed by diffing fact sets, every entity carrying `provenance: "derived"` and evidence anchors. Grouping: files roll up into a parent entity per top-level source directory (e.g. `src/routes` → "Routes" system) — crude but honest; AI refines labels later, marked `inferred`.

Tests: added route on branch → route entity `headState: "added"`; renamed file keeps stable entity id when symbol survives; deleted file → `removed`.

Commit: `feat(core): evidence graph with stable ids and change states`.

### Task 12: Change-unit grouping + commit classification

**Files:**
- Create: `packages/core/src/changeUnits.ts`
- Test: `packages/core/src/changeUnits.test.ts`

Group changed entities into `ChangeUnit`s per commit (one unit per commit initially; entities changed by the commit attach to it). Classification rule (from design): commits whose message starts with `fixup!`/`squash!`, merge commits, and diffs that are whitespace-only (`git diff -w` empty) are flagged `grouped: true` with reason — they don't get their own chapter but stay in the timeline. Technical titles come from commit subjects (`derived`); human titles left null for the narrator.

Tests use the demo fixture branch: 2 meaningful units, fixup commit grouped, formatting commit grouped.

Commit: `feat(core): semantic change units with fixup/formatting grouping`.

### Task 13: Narration request/response + claim validator

**Files:**
- Create: `packages/core/src/narration.ts`
- Test: `packages/core/src/narration.test.ts`

`buildNarrationRequest(manifest)` → JSON containing facts only, plus the allowed id lists. `applyNarration(manifest, response)` → validates then merges:

Rules (each is a test):
- Response may only reference existing entity/changeUnit ids → unknown id rejected with actionable error list.
- Response fields land only in narration slots (humanLabel, summary, beforeDescription, afterDescription, userImpact, openQuestions) — attempts to set `provenance`, `evidence`, or states are rejected.
- Everything merged is stamped `provenance: "inferred"` + optional confidence; a response claiming `derived` is rejected.
- Missing narration → slots stay null; renderer falls back to technical labels (template narrator).
- `templateNarrator(request)` produces deterministic dry narration (used by tests and no-agent mode).

Commit: `feat(core): validated narration loop with template fallback`.

### Task 14: Book skeleton projection

`packages/core/src/book.ts`: builds the ten-chapter `BookManifest` — `purpose` (from package metadata + top-level entities), `systems` (grouped architecture), `history` (commit timeline) as `generated`; the other seven as `not-written`. Test: exactly ten chapters, correct statuses, validates against schema from Task 4.

Commit: `feat(core): ten-chapter book skeleton projection`.

## Phase 6 — Renderer (`@gitiviz/renderer`)

### Task 15: Escaping + HTML shell

**Files:**
- Create: `packages/renderer/src/escape.ts`, `packages/renderer/src/render.ts`
- Test: `packages/renderer/src/escape.test.ts`, `packages/renderer/src/render.test.ts`

`escape.ts`: `escHtml`, `escAttr`, `safeUrl` (allowlist `https:` + configured repo origins; anything else → `null`, rendered as plain text). Tests: `<script>` filename neutralized; `javascript:` link dropped; unicode intact.

`render.ts`: `renderChangeBook(book, change) => string` — one self-contained HTML document. **Visual style (user-mandated): clean, standard, low cognitive load — light theme only in v0.1.** Inline CSS: system font stack, generous whitespace, neutral grays + one accent color, no gradients/badges/decorations. Do NOT ship a dark scheme in v0.1 (a polished one may come later; an auto-inverted messy one never). CSP: `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src 'unsafe-inline'; img-src data:;">` — **no `<script>` at all in v0.1**: chapter switching uses CSS `:target` / radio-input technique so the CSP can ban scripts entirely. Chapters render as `<section>` per change unit + branch overview; evidence inside `<details>` (collapsed); before/after flows as semantic HTML lists with verb-labelled arrows (`──creates order──▶` as text), max 5 nodes per row via CSS grid.

Render tests (string/DOM via happy-dom): exactly one section visible by default; `<details>` present and closed; hostile labels escaped in output; zero `<script>` tags; no `http://` references except allowlisted source links.

Commit: `feat(renderer): self-contained scriptless HTML change book`.

### Task 16: Responsiveness + accessibility checks

Add tests: every interactive control reachable via native elements (radio/label/anchor — no click-handler divs); `lang`, landmarks, skip link present; long tokens wrapped (`overflow-wrap`) so 320px has no horizontal scroll (assert CSS rules present; visual check manual). Commit: `feat(renderer): a11y and small-screen hardening`.
